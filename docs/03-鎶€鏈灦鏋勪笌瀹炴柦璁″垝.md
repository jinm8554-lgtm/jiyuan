> 项目路径：`/home/ubuntu/aetherfall`（全新初始化，未复用任何既有游戏项目、代码、素材或数据库）

## 1. 技术栈总览

| 层 | 技术 | 说明 |
|---|---|---|
| 前端 | React 19 + TypeScript + Tailwind 4 + wouter | 页面/组件分层，纯 tRPC 数据流 |
| 状态/数据 | tRPC 11 + TanStack Query | 端到端类型安全；无手写 REST/Axios |
| 后端 | Express 4 + tRPC (`server/routers/*`) | 业务用例层，服务端权威 |
| 领域逻辑 | `server/game/*`（纯函数模块） | 战斗、公式、抽卡、AI、备份，全部可单测 |
| 数据 | MySQL/TiDB + Drizzle ORM | Schema + drizzle-kit 迁移 |
| 资源 | S3（storagePut/StorageProxy） | 立绘、地图底图、备份文件 |
| 账号 | Manus OAuth（会话 Cookie） | 服务端会话，客户端不接触 Token |
| AI | 会话内 LLM 网关 + GM 可配置的 OpenAI 兼容 Base URL | 结构化 JSON 输出 + Schema 校验 |
| 测试 | Vitest | 单元 / 接口（tRPC caller）/ 核心流程 |

## 2. 分层架构

```
┌─────────────────────────── 表现层 (client/src) ───────────────────────────┐
│ pages/（路由页）  components/game/（游戏 UI 原语）  components/ui/（基础控件）│
│ 只负责渲染 + 调用 tRPC；不包含任何战斗/抽卡/数值公式                        │
└───────────────────────────────────┬───────────────────────────────────────┘
                                    │ tRPC（/api/trpc，类型安全）
┌───────────────────────────────────▼───────────────────────────────────────┐
│ 接口层 server/routers/*           — 参数校验(zod)、鉴权、编排、错误语义     │
├───────────────────────────────────────────────────────────────────────────┤
│ 领域层 server/game/*              — 纯函数规则引擎（无 IO，可 100% 单测）   │
│   formulas.ts 战斗/属性公式   battle.ts 回合引擎   recruit.ts 抽卡与保底    │
│   ai.ts 角色 AI 编排与校验    progression.ts 结算  backup.ts 备份/恢复      │
├───────────────────────────────────────────────────────────────────────────┤
│ 数据访问层 server/db.ts           — Drizzle 查询助手，返回原始行            │
├───────────────────────────────────────────────────────────────────────────┤
│ 持久层 drizzle/schema.ts + 迁移   — 28 张表；玩家数据与策划配置分离        │
├───────────────────────────────────────────────────────────────────────────┤
│ 资源层 server/storage.ts (S3)     — 图片与备份文件；DB 只存 URL/key         │
└───────────────────────────────────────────────────────────────────────────┘
```

**核心原则**

1. **数值不落前端**：稀有度概率、保底、成长率、掉落表、战斗公式全部在服务端；前端只做展示。
2. **策划配置进数据库**：角色、技能、装备、建筑、地图节点、任务、剧情、招募池、AI 配置均为表；GM 后台改动即时生效，客户端无需发版。
3. **规则与 IO 分离**：`server/game/*` 不引入数据库依赖，输入输出为普通对象，便于单测与未来抽离为独立服务。
4. **存档只在服务端**：不使用 localStorage/JSON 作为正式存档，仅缓存 UI 偏好（如面板折叠）。
5. **密钥永远不落前端**：AI API Key 仅存服务端数据库，读取接口一律返回掩码（`sk-****abcd`）。

## 3. 数据模型（28 张表 / 六域）

| 域 | 表 |
|---|---|
| 账号与安全 | `users`、`apiTokens`、`adminAuditLogs` |
| 玩家存档 | `gameProfiles`、`playerCharacters`、`playerEquipment`、`teams`、`profileBuildings`、`profileProgress`、`regionStates`、`profileQuests`、`profileStoryFlags`、`profilePity` |
| 策划配置 | `characters`、`skills`、`equipments`、`buildings`、`regions`、`worldNodes`、`quests`、`storyScenes`、`recruitPools`、`events`(领地事件) |
| 战斗 | `battles`、`battleLogs` |
| AI | `aiConfigs`、`aiModels`、`aiConversations`、`aiMessages`、`aiCallLogs` |
| 招募与运维 | `recruitHistories`、`backupRecords` |

**迁移机制**
- 结构迁移：`drizzle-kit generate` 产出 SQL → 由 `webdev_execute_sql` 应用（生产同路径）。
- 数据迁移：`dataMigrations` 表记录已执行的数据级迁移（如新增字段回填、策划数据版本升级），由 `server/game/dataMigrations.ts` 幂等执行。
- 客户端更新不覆盖玩家数据：所有存档表主键独立于前端版本；策划表与存档表通过业务键（`charKey`/`nodeKey`）关联，删除策划数据不影响存档（读取时使用快照字段回退）。

## 4. 关键流程设计

### 4.1 领地资源（离线结算）
```
读取 profile → elapsed = now - lastTickAt（上限 12h）
           → 产出 = Σ(建筑等级产出) × 效率加成(城墙/市场)
           → 受存储上限约束 → 写回并更新 lastTickAt
```
纯函数 `accrueResources(profile, buildings, now)`，可单测。

### 4.2 战斗（服务端权威）
```
startBattle(nodeKey, teamId)
  → 校验体力/解锁/队伍 → 生成战斗状态（单位、行动序、能量、冷却）
  → 落库 battles.state
act(battleId, action)         // 玩家回合
  → 服务端结算：命中/暴击/元素克制/减伤/状态/能量 → 追加 event log
  → 敌方 AI 行动 → 判定胜负 → 若胜，结算奖励并推进节点进度
autoResolve(battleId)         // 半自动
  → 服务端快速推演至结束，返回完整 log 与结算
```
伤害公式：
```
基础 = 攻/魔 × 技能倍率 × (1 + 等级差修正)
减伤 = 100 / (100 + 有效防御)
元素 = 克制 1.5 / 被克 0.75 / 同系 1.0
暴击 = 1 + 暴击伤害；命中/闪避按命中率判定
最终 = max(基础 × 减伤 × 元素 × 暴击, 基础 × 0.1)
```

### 4.3 招募（配置驱动 + 保底）
```
拉取卡池配置(概率表/保底参数/开放时段)  ← 数据库，前端不可覆盖
抽取：权重抽样 → 命中稀有度 → 在该稀有度内随机可用角色
保底：软保底区间线性加权；硬保底必出 SSR；十连必含 1 SR+
重复：转「星辉信物」+ 羁绊提升，不再重复入库
记录：recruitHistories + profilePity（事务内更新）
```

### 4.4 AI 角色互动（在场角色约束）
```
请求 → 校验 conversation 与「在场角色」集合（仅当前选中角色）
     → 构建角色上下文（背景/性格/目标/价值观/关系/剧情状态/羁绊/场景）
     → 调用 GM 配置的模型（Base URL / Key / 模型；客户端不可覆盖）
     → JSON Schema 校验 → 业务校验（角色 ID 必须属于在场集合、长度、字段枚举）
     → 违规条目丢弃并记录 aiCallLogs（violation 计数）
     → 落库消息、应用羁绊变化、返回结构化 turns
无配置/失败 → 本地脚本回退（明确标注「本地回退」），保证功能可用
```

## 6. 非功能需求落实

| 需求 | 落实 |
|---|---|
| 全页面状态完整 | 统一 `AsyncBoundary`（loading skeleton / empty / error+重试 / 成功） |
| 网络异常 | Query 重试 1 次 + 全局错误提示；变更操作 toast 反馈 |
| 会话过期 | `UNAUTHORIZED` → 引导重新登录（不静默失败） |
| 数据库异常 | `getDb()` 返回空 → 接口返回 `PRECONDITION_FAILED` 语义化提示 |
| 图片加载失败 | `ArtImage` 组件统一 `onError` → 自绘纹章占位符 |
| AI 返回错误 | Schema 校验 + 重试 1 次 + 本地回退 + 日志留痕 |
| 移动端适配 | 三断点策略（<768 / 768–1279 / ≥1280），触摸目标 ≥44px |
| 安全 | 无密钥入库前端；Token 存哈希；管理员接口 `adminProcedure`；输入 zod 校验 |
| 备份恢复 | `backupRecords` + S3 JSON 快照，支持恢复校验与审计 |

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 无服务器冷启动 + 战斗状态体积 | 战斗状态精简为纯数值 + 事件数组；单次请求 < 180s |
| AI 返回不可控 | JSON Schema + 在场角色白名单 + 长度上限 + 本地回退 |
| 图片资源体积 | 立绘 512×680、地图 1536×1024 压缩后上传 S3，前端 `lazy` + 占位 |
| 数值膨胀 | 成长率按稀有度分层（R/SR/SSR 系数），伤害以「减伤曲线」抑制溢出 |
| 后台误操作 | 全量后台写操作写 `adminAuditLogs`；备份恢复需二次确认 |
